# 设计说明

> 记录「为什么这么做」，而不是「做了什么」。每个取舍背后都有一个具体的失败场景。
> 规则本身的判定逻辑见 [考勤规则设计.md](考勤规则设计.md)。

## 1. 一句话定位

不是"点一下打卡"，而是**一条能被第三方独立验证的考勤证据链**。

判断一个打卡系统是否合格，问三个问题就够了：

1. 员工改手机时间能不能"永不迟到"？ → 服务端授时
2. 员工在家能不能"到公司打卡"？ → 围栏 + 精度门槛（服务端复算）
3. HR 事后改一条记录，能不能被发现？ → 哈希链 + 审计日志

三条都答"不能"才算及格。本项目三条都做了，本地/云端双模式都实现（本地版第二条弱一些，如实标注）。

## 2. 为什么逻辑抽到 `core/`

`core/` 三个文件（rules / ledger / sha256）**不含任何 `wx.*` 调用**，纯函数。换来三件事：

1. **能被 Node 直接单测**，不用启动开发者工具，几毫秒跑完 26 个用例
2. **云端能复用同一套规则**（`_shared/common.js` 复制了一份，另有交叉比对测试）
3. **网页预览、CLI 工具都能复用**，不用重写

代价是云端和客户端有两份实现。我用测试压住风险：只要两边算出的 hash 不一致，`hash-consistency.test.js` 立刻红。

## 3. 时间：固定 UTC+8，at ≠ createdAt

- **固定时区**：员工出差到东京，手机时区变 +9，按本地时区算"今天"会提前一小时切换，
  导致 23:30 的卡跑到明天。所以 `dayKeyOf(ms)` 永远按 +8。跨国项目改一个常量即可。
- **`at` / `clientAt` / `createdAt` 三者分家**：
  - `at` = 打卡动作发生的时间。云模式 = 服务端 `Date.now()`
  - `clientAt` = 手机上报的时间。差 >90 秒 → 打 `timeSkew`（这台设备时钟不对）
  - `createdAt` = 落库时间。补卡审批时 `at` 是补的那天、`createdAt` 是今天，差很远。
    混用会让月统计错得离谱。

## 4. 定位：为什么精度参与判定

最常见的"打卡神器"是改定位或假 GPS。光算"点在圆内"没用——改出来的点也在圆内。

所以判定用两个条件：`dist - accuracy <= radius` **且** `accuracy <= radius`。
含义是"以上报坐标为圆心、以上报精度为半径的圆必须基本落在打卡圈里"。

副作用是室内定位差时打不上卡。所以保留三条逃生路（见规则文档 §5）：
`strictGeo=false`、`allowSkipGeo=true`、外勤打卡必填备注。
三条都不是"绕过校验"，而是"把不确定性显式记录交给人判断"。
考勤系统的目标不是 100% 自动化，而是**让异常可追溯**。

## 5. 哈希链：能证明什么、不能证明什么

**能证明**：
- 记录没被本机改过（改任何字段，`verifyChain` 定位到第几条）
- 顺序没被插入/删除（`seq` 连续 + `prevHash` 串起来）
- 服务端模式下，记录没被数据库后门改过（云函数写入时复算 hash）

**不能证明**：
- 记录本身是真的（客户端可以一开始就伪造，然后用正确算法算出 hash）
- 设备时间是真的（本地模式下 `at` 就是客户端时间）

所以 README 明确写：**要防伪造必须走云端**。这是本项目与"声称能防作弊的打卡 App"的分界线。

链的实现细节（踩过的坑）：
- 必须用**排序键的 stable JSON**，不能直接 `JSON.stringify`。否则对象字段插入顺序不同 →
  同一内容不同 hash → 两端不一致。这个 bug 真踩了，是 `hash-consistency.test.js` 抓出来的。
- 数值要归一化（`lat` 6 位、`acc`/`dist` 1 位、时间取整），否则浮点尾数导致哈希漂移。
- 中文备注**不能转义**（`ensure_ascii=False`），Python 默认会转成 `\uXXXX`，两端就对不上。
- **参与哈希的是字段白名单**，不是整个对象。`shiftName`、`wifiSsid` 这类展示层派生信息
  不参与哈希——改它不应该让记录变成"被篡改"（有专门测试钉住这条）。

## 6. 双模式：为什么默认本地

- 90% 的人第一次打开只想看看效果，要求先开通云开发、建 6 个集合、配权限——大概率直接放弃。
- 本地模式功能完整（除防伪造），能真实用起来，也能离线演示。
- `cloud.js` 有 `ENV_ID` 空值即降级的设计，页面代码一行不用改。

代价是所有写操作要写两遍。`utils/punch.js` 做编排层吸收差异——页面只调 `doPunch()`。

## 7. UI 为什么从深色改浅色

v1 是深色主题。改浅色的理由：

1. **使用场景在户外**：早上 8 点在楼下打卡，屏幕反光下深色的对比度塌掉，浅色可读性好得多。
2. **打卡是高频短操作**：一天开 4-6 次，每次停留 10 秒。信息密度高、对比清楚比"好看"重要。
3. **状态色需要准确**：深色底下绿色/琥珀色都会发灰，异常状态容易看不出。
   浅色底上 `#10b981`（正常）/ `#f59e0b`（异常）/ `#ef4444`（严重）能一眼区分。

主渐变只用一个（靛蓝→紫），辅助色严格按语义分配，不做"彩虹配色"。

## 8. 为什么删掉薪酬统计

v1 有计薪模块。v2 移除，理由：

- 考勤系统的职责是**记录出勤事实**，发多少钱是 HR 与薪资系统的事。
- 真实风险：一旦算错，用户会去质疑考勤数据本身的准确性——而考勤数据是对的。
  职责混淆会连带损害核心资产（可信记录）的可信度。
- 钉钉本身也把考勤与算薪拆成两个应用。

`pages.test.js` 里有一条硬断言：页面 data 与导出 JSON **不允许出现** `pay`/`salary`/`wage` 等键。
防止以后有人"顺手加回来"。

## 9. 可扩展方向（按投入产出排序）

1. **节假日日历**：加班倍数需要法定节假日表（每年不同，且调休日不是周末）
2. **逐日排班表**：现在只有周期轮换，真实排班需要一天一天改
3. **多打卡点**：连锁门店需要多围栏 + 按人分配
4. **BLE 信标辅助**：室内 GPS 差是硬伤，蓝牙信标比 WiFi 可靠（`wx.startBeaconDiscovery`）
5. **外出/出差单据**：有了才能把午休外出从工时里剔除（当前是已知不足）
6. **导出 Excel**：现在只有 JSON 复制。HR 要 xlsx
7. **企业微信/钉钉组织同步**：现在员工档案靠首次登录自动建，没有部门/上级
8. **人脸/活体**：防同事代打卡，需资质，最后做

## 10. 已知不足（如实列出）

见 [考勤规则设计.md §9](考勤规则设计.md)。核心三条：
- 自由工时/弹性班的中途外出计入工时（无外出单据）
- 云端与客户端两套规则实现，靠测试保证同步而非绝对一致
- 无节假日日历、无多打卡点、排班不支持逐日编辑
