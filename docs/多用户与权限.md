# 多用户与权限

> 2026-10-31。需求：**一个人是管理员，其他人加入这家公司；员工只能打卡等操作，不能触碰规则。**

## 一、权限模型：四档角色

不是简单两分（管理员/员工），因为真实团队里"能改规则的"和"能批补卡的"往往不是同一批人。

| 角色 | 能改规则 | 能审批 | 能看全员数据 | 能管成员 | 其他 |
|---|---|---|---|---|---|
| **创建者** owner | ✅ | ✅ | ✅ | ✅ | 唯一可转让/解散的人 |
| **管理员** admin | ✅ | ✅ | ✅ | ✅ | 日常管理 |
| **主管** manager | ❌ | ✅ | ✅ | ❌ | 只看数据、审批 |
| **员工** member | ❌ | ❌ | ❌ | ❌ | 打卡、申请补卡、看自己 |

关键约束：**员工不能改规则**。这条由 20 条测试钉死（`tests/permissions.test.js`）。

## 二、三层防线（缺一层就有洞）

这是本文档最重要的一节。**权限不能只做在前端**。

| 层 | 做什么 | 位置 | 强度 |
|---|---|---|---|
| **1. 前端 UI** | 不给入口：员工看不到编辑按钮、改角色按钮、邀请码 | `webapp/app.js`、`pages/rules` | 弱（用户可改代码） |
| **2. 前端函数** | `canDo()` 拦截每一次写入调用 | `core/permissions.js` | 弱（同上，但能防误触） |
| **3. 云函数** | **服务端按 openid 查真实角色，越权直接返回 FORBIDDEN** | `cloudfunctions/company`、`punch` | **强（唯一可靠）** |

前两层是"体验"，第三层是"安全"。文档里写清楚，比假装前端权限是安全的好。

## 三、修掉的真实越权漏洞

改之前 `cloudfunctions/punch/index.js` 里是：

```js
// ❌ 服务端直接接受了客户端传来的规则
const rs = C.normalizeRuleSet(payload.ruleSet || cfg.ruleSet);
```

这意味着**员工改前端代码就能传一个 `{start:'00:00', lateGrace:600}` 的规则**——
迟到永远不判、围栏也形同虚设。

改成：

```js
// ✅ 有公司归属时，只用服务端规则，忽略客户端传的
if (companyId === 'default' || !cfg.ruleSet) {
  rs = C.normalizeRuleSet(payload.ruleSet || cfg.ruleSet);  // 单机模式
} else {
  rs = C.normalizeRuleSet(cfg.ruleSet);                      // 公司模式：服务端为准
  // 客户端规则与服务端不一致 → 记审计（可能是越权尝试）
}
```

单机模式仍允许客户端传规则，因为那时本来就没有"管理他人"的需求。

## 四、加入流程

```
管理员（创建者）
  │  ① 创建公司（首次打开自动完成）
  │  ② 拿到 6 位邀请码（如 CN3T58）
  ↓  ③ 把码发给同事
员工
  │  ④ 输入邀请码 → 加入
  │  ⑤ 角色**硬编码为 member**（服务端不接受客户端传来的 role）
  ↓  ⑥ 只能看到打卡/记录/统计/我的，规则页只读
```

### 邀请码设计

- **6 位，字符集 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`**——刻意去掉 `0/O`、`1/I/l`，因为员工要在手机上手动输
- 约 30⁶ ≈ 7.3 亿组合，一个公司足够
- 大小写、空格、连字符自动容错（`ab-cd12` → `ABCD12`）
- 管理员可随时更换，旧码立即失效（已加入的人不受影响）
- **只有能邀请的角色才能看到完整邀请码**；员工看到的是"请向管理员索取"

## 五、几个容易被忽略的设计决定

### 1. 加入时角色硬编码，不接受客户端传

```js
// ✅ 正确
role: 'member',

// ❌ 错误（可以自己填 role:'admin' 直接升权）
role: payload.role || 'member',
```

### 2. 不能把最后一个管理员降级

否则公司里没人能改规则了，变成死锁。

### 3. 移除成员不删打卡记录

考勤数据不能因为离职而消失——这是审计要求。移除只是把 `status` 改成 `removed`。

### 4. 规则变更必须留痕

`pc_audit` 记 `openid / kind / at / role`。出了争议要能查到"谁在什么时候改了什么"。

### 5. 前端只读不是"藏起来"

员工的规则页不是把按钮删掉就完事，而是：
- 顶部一句明确说明："考勤规则由管理员统一设置，你可以查看但不能修改"
- 所有参数用**不可点的静态行**展示
- 选项标 `readonly`，点击弹提示而不是静默无效

显式说明比"悄悄消失"好——用户不会以为界面坏了。

## 六、网页版怎么验证（无需后端）

网页版没有后端，`webapp/company.js` 用 localStorage 模拟"同一设备上的多个身份"，
用来验证权限模型是否正确：

1. 打开 → 自动建公司，你是**创建者**
2. 「我的 → 公司与成员」→ 看到邀请码
3. 点「用邀请码加入一个员工」→ 自动切换到员工身份
4. 进「考勤规则」→ 只能看，没有任何编辑入口
5. 进「公司与成员」→ 看不到邀请码、没有改角色/移除按钮

> 这能验证权限**逻辑**，但不是真实的多用户隔离。
> 真实隔离必须靠云开发的 openid + 云函数判权。

## 七、上线到真团队（需要云开发）

| 步骤 | 说明 |
|---|---|
| 1 | 开通云开发，填 `ENV_ID` |
| 2 | 建集合：`pc_companies`、`pc_members`、`pc_users`（另有 `pc_punches` 等） |
| 3 | 部署 4 个云函数：`login`、`company`、`punch`、`admin` |
| 4 | 权限全设「仅创建者可读写」，业务读写全走云函数 |
| 5 | 第一个注册的人 → 数据库手改 `pc_users.role = 'owner'` |

详细见 [部署与接入.md](部署与接入.md)。

## 八、测试

```bash
node tests/permissions.test.js    # 20 条，权限矩阵
node scripts/test-permissions.js  # 真实浏览器跑完整流程（管理员加员工→切视角验证）
```

`permissions.test.js` 里最关键的一条：

```
★ 只有 owner/admin 能改考勤规则（这是本需求的核心约束）
```

以及：

```
★ 模拟真实场景：员工加入后什么都改不了，但能打卡
```

第二个测试会断言员工**被拒绝的动作 ≥ 10 个**，防止有人为了"方便"悄悄放权。

## 九、已知限制（如实说明）

1. **网页版的"多身份"是模拟的**，不是真实隔离。同事之间看不到彼此的数据，要等云开发。
2. **小程序端的团队页尚未完成**（核心权限模块和云函数已就绪，页面复用现有 patterns）。
3. **没有"加入申请/审批"流程**：拿到邀请码即加入。真实公司可能要管理员审批，这是下一步。
4. **没有部门/分组**：主管目前能看全员，不能只看本组。真实组织需要 `departmentId`。
5. **邀请码无过期时间**：只能手动更换。可加 `expiresAt`。
