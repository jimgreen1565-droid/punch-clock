# 考勤规则设计（对齐钉钉模型）

> 这份文档记录「四种考勤规则怎么判、为什么这么判」。每个规则都对着钉钉真实产品语义做的，
> 改代码前先看这里，能避免把「弹性班的早退」这种本不该存在的概念写进去。

## 1. 四种考勤规则类型

钉钉的考勤组类型分为「固定班制 / 排班制 / 自由工时」，弹性工作制是固定班制的一种变形。
本项目把它拆成**四种平级可选类型**，切换随时可做（钉钉里创建后不可改，只能新建考勤组）。

| 类型 | id | 判定什么 | 典型场景 |
|---|---|---|---|
| 固定班制 | `fixed` | 上班迟于 `start+lateGrace` 算迟到；下班早于 `end-earlyGrace` 算早退；`end` 之后算加班 | 写字楼、行政、客服白班 |
| 弹性工作制 | `flexible` | **只**看是否晚于 `latestStart`（算迟到）+ 当日工时是否满 `requiredMinutes`（不足算工时不足） | 研发、设计、管理层 |
| 排班制 | `shift` | 按排班表取当天班次，判定同固定班制；支持周期轮换（三班倒） | 工厂、门店、医院、客服轮班 |
| 自由工时 | `free` | **不判**迟到早退旷工，只累计「最早上班→最晚下班」的时长，对标 `dailyTargetMinutes` | 家政、装修、外勤销售、物流 |

### 为什么弹性班没有「早退」

弹性工作制的产品语义是：你几点来不重要，把该干的时长干完就行。
所以 `classifyPunch('out')` 在 `flexible` 下永远返回 `normal`——早退这个概念在此不成立。
真正该判的是「今天够不够工时」，由 `pairDay` 的 `shortMinutes` 负责，且**容忍 15 分钟抖动**
（否则每天 17:58 打卡都会被判「工时不足 2 分钟」，用户会疯）。

弹性班的应下班时间是**滑动**的：

```
expectOutAt = max(earliestEnd, 实际上班时刻 + requiredMinutes + 午休)
```

09:00 上班 → 17:30（顶到 earliestEnd）
09:30 上班 → 17:30（09:30+8h=17:30，取 max 仍是 17:30）
10:00 上班 → 18:00

测试 `rule-compare.test.js` 里用四个 inMin 逐一钉死了这条曲线。

### 为什么自由工时不判「休息日」

自由工时的从业者没有固定周末（家政可能周六上班、周三休息）。
所以 `shiftOfDay` 对 `free` 永远返回 `rest: false`，`plannedDays` 返回整月天数。
如果强行按周末判休息，这类用户会看到「今天是休息日」而不能打卡——产品上是错的。

## 2. 上班卡与下班卡怎么配对

一天可能打很多次卡（外出、忘打补打、审批补卡）。配对规则：

- **上班卡**取当天**最早**的一条 `type=in`
- **下班卡**取当天**最晚**的一条 `type=out`
- 工时 = 下班 - 上班 - 午休窗口重叠部分

这个规则对自由工时有个已知副作用：中午外出两小时会被算进工时（钉钉的「外出」需要单独申报，
本项目没做「外出/出差」单据，所以承认这个简化，写进 §9 已知不足）。

## 3. 迟到 / 早退 / 加班 / 缺卡 / 旷工 的判定顺序

一天只有一个「主状态」，优先级从高到低：

```
rest（休息日且无打卡）
  > absent（全天无记录，且已过下班 2 小时）
  > missing（有上班无下班，或缺上班）
  > late（迟到）
  > early（早退）
  > under（工时不足，仅弹性）
  > overtime（有加班分钟数）
  > normal
```

为什么迟到压过早退：员工既迟到又早退时，先说"迟到"更符合直觉，分钟数两个都会算进
`lateMinutes` / `earlyMinutes`，只是标签取一个。统计页的「异常」两个都计入。

### 缺卡的 2 小时宽限

`missingIn` / `missingOut` 的判定都延后 2 小时：

- 09:00 应上班，12:00 还没上班卡 → 判缺卡（而不是 09:05 就判）
- 18:00 应下班，20:00 还没下班卡 → 判缺卡（而不是 18:01 就判）

原因：18:10 打个下班卡是常态，18:00 就标红会让红点天天闪。

## 4. 跨天班次如何归属

夜班 21:00-06:00 的下班卡在凌晨 03:00 打，必须归到**前一天**的班次。
`resolveShiftDay` 用两级判定（顺序很重要）：

1. **强匹配**：打卡时刻落在某班次窗口内（`inAt ≤ t ≤ outAt`）。先今天，再昨天。
2. **弱匹配**：落在窗口外的容忍带（提前 30 分钟 ~ 延后 6 小时）。先今天，再昨天。

为什么必须强匹配优先：假设今天有 08:00 早班、昨天有 21:00-06:00 夜班。
凌晨 03:00 的打卡既在「今天的提前容忍带」内，也在「昨天的正式窗口」内。
只按顺序试（先今天）会错归到今天 → 夜班员工每天缺下班卡。这是个真实踩过的坑。

## 5. 一天打满之后怎么办

上下班卡都齐了以后再点打卡，**不再猜「该打哪个」**，而是明确返回 `stage: 'done'`：

- 首页按钮变成「已完成」（降饱和，视觉上不可再打）
- 点击弹确认层：「今日已完成打卡 · 上班 08:50 · 下班 21:22 · 工时 11h32m — 补一条？」
- 只有用户明确点「补一条」，才按时间远近归到上班或下班并写入

为什么这样设计：之前写成「上下班齐了就回落到 in」，导致按钮显示「上班打卡」、
点一下悄咪咪又写一条上班卡，与「今日已完成打卡」文案自相矛盾。
这种"看起来能点但语义错误"的交互比直接禁用更糟。

## 6. 打卡范围：为什么精度要参与判定

判定用两个条件同时成立：

```
dist - accuracy <= radius      且      accuracy <= radius
```

含义：以你上报坐标为圆心、上报精度为半径画圆，这个圆必须基本落在打卡圈内。
±600 米的定位即使圆心正好在公司也无法证明你在——直接拒绝，理由 `low-accuracy`。

### 三条逃生通道（都不是绕过校验，是让异常可见）

| 配置 | 行为 | 适用 |
|---|---|---|
| `geo.strict = true`（默认） | 范围外禁止打卡 | 防代打卡 |
| `geo.strict = false` + 必填备注 | 允许打卡，标 `outOfRange` + 进待审核 | 有外勤岗的团队 |
| 定位 API 失败 | 允许打卡，标「未定位待审核」，必须备注原因 | 电梯/地下室 |

第三条尤其重要：产品目标不是 100% 自动化，而是**让异常可追溯**。

## 7. 打卡方式（钉钉有、本项目实现情况）

| 钉钉能力 | 本项目 | 说明 |
|---|---|---|
| 地理位置打卡 | ✅ | 圆形围栏 + 精度门槛，服务端复算 |
| WiFi 打卡 | ⚠️ 部分 | 记录 `wifiSsid` 但**不作为唯一判定**：小程序拿 SSID 在 iOS 上受限 |
| 蓝牙打卡 | ❌ | 需要 BLE 信标，未做 |
| 考勤机/人脸 | ❌ | 需要硬件与资质 |
| 外勤打卡 + 备注 | ✅ | 范围外填原因，进待审核 |
| 拍照打卡 | ❌ | 未做（需要相册/相机权限流程） |
| 补卡申请 + 审批 | ✅ | 审批通过生成 `source=patch` 的新记录接入哈希链，不改历史 |
| 法定节假日自动排休 | ❌ | 未做，需节假日表（每年不同，且调休日不是周末） |

## 8. 不做薪酬统计

本版**移除了**计薪模块（v1 有的 payroll）。原因：

- 考勤系统的职责边界是「记录出勤事实」，发多少钱是 HR 与薪资系统的事。
- 把薪酬算进打卡 App 有一个真实风险：一旦算错，用户会去质疑考勤数据的准确性，
  而考勤数据本身是对的。职责混淆会连带损害核心资产的可信度。
- 钉钉本身也是把考勤与薪资（算薪）拆成两个应用的。

所以统计页只统计：出勤率、异常分布、工作时长、近 7 日趋势。
测试 `pages.test.js` / `web.test.js` 里有一条硬断言：页面 data 与导出 JSON 里**不允许出现**
`pay` / `salary` / `wage` / `deduct` 等键——防止以后有人"顺手加回来"。

## 9. 出勤率的口径

```
出勤率 = 有上班卡的工作日数 / 应出勤工作日数
```

不是「正常天数/应出勤」——那样一个迟到日就把率拉低，指标会失真。
加班日仍然是出勤日（人来了）。异常单独计数展示。

「应出勤工作日数」按当前规则算：固定班制去掉周末；排班制去掉 `REST` 槽；
自由工时算整月。换规则会改变分母，这是设计如此（规则变了，"应出勤"的定义就变了）。

## 10. 已知不足（如实列出）

1. **自由工时/弹性班的中途外出计入工时**：没有「外出/出差」单据，中午离开两小时会被算作工作。
2. **无节假日日历**：法定假日与调休日不支持，加班倍数（1.5/2/3）只留了参数位。
3. **云端与客户端两套规则实现**：云函数不能 require 小程序模块，所以 `_shared/common.js`
   复制了一份判定逻辑。`rule-compare.test.js` 与 `server-rules.test.js` 里有交叉比对，
   但不保证 100% 同步。彻底解法是抽 npm 包两端共用。
4. **排班表只能设「周期轮换」**：不支持逐日手动排班（钉钉的排班表可以一天一天改）。
5. **多打卡点不支持**：单圆围栏。连锁门店需要多围栏 + 按人分配。
6. **Web 版数据不跨设备**：存在浏览器 localStorage，换手机就没了。这是单机版的取舍，
   团队用必须上云开发（小程序端已实现）。
